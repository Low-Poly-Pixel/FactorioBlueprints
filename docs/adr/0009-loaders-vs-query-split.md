# TanStack Query only on the browse/filter page; loaders everywhere else

Data fetching defaults to TanStack Start's own route loaders + `createServerFn`, with no query-caching library. The one exception is the browse/search page: its loader still runs for the initial SSR hit, but seeds a client-side `useQuery`/`useSuspenseQuery` so filter/search interactions after hydration hit the cache instead of re-running a full loader per keystroke or toggle. Search and filter values (title search, entity/item type, game version, "requires Space Age") live in TanStack Router's typed search params, never in component state or Context — that's what lets the loader/Query re-run on the right param changes and keeps filtered views shareable/bookmarkable as URLs.

We decided against TanStack Query everywhere because per [ADR-0004](0004-anonymous-immutable-mvp.md), uploaded Blueprints/Books/Planners are immutable — a detail-page fetch by ID has no staleness or invalidation problem for Query to solve, and TanStack's own docs describe the router's built-in loader cache as "a good fit for smaller to medium size applications" like this one. The browse page is the one place that condition doesn't hold: filters are repeatedly re-queried by the same user (confirmed scope, not hypothetical), which is exactly the caching problem Query exists for. We considered using Query everywhere for consistency, or nowhere for simplicity, and rejected both: everywhere adds a dependency and cache-invalidation surface with nothing to invalidate on the detail/upload pages; nowhere means every filter toggle re-runs a full loader when a previously-seen filter combination could instead be an instant cache hit.
